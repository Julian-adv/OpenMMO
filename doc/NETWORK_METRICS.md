# 네트워크·정적 파일 전송 지표

대시보드의 **네트워크 대역폭**과 **정적 파일 전송 순위**는 운영자 인증이 적용된 `/api/metrics/network`, `/api/metrics/asset-traffic`에서 조회합니다. 조회 기간은 1시간·24시간·7일·30일입니다.

## 수집 방식과 부하

- 네트워크는 기본 60초마다 외부 인터페이스의 누적 송신·수신 카운터를 읽습니다. 실제 경과 시간으로 나누어 평균 속도를 계산합니다.
- 게임의 접속 계정 수만 짧게 가져와 크기 1의 채널로 넘깁니다. 채널이 차면 해당 수집을 건너뜁니다. 5초 이상 밀린 접속 스냅샷은 사용하지 않습니다.
- 전용 `traffic-metrics` 스레드가 시스템 파일 읽기, 로그 해석, 지표 저장을 수행합니다. 게임 처리 스레드에서 이 작업을 기다리지 않습니다.
- 로그는 10분마다 이전 위치부터 최대 2 MiB를 읽습니다. 해석은 100ms 또는 파일·시간별 집계 항목 4,096개에서 멈춥니다. 읽기·DB 저장 시간은 이 100ms에 포함되지 않습니다. 처리하지 못한 부분은 다음 주기에 이어 읽고, 밀린 바이트를 화면에 표시합니다.
- 게임 DB와 별도로 `<STATE_DIR>/network_metrics.db`에 저장합니다. WAL 모드와 짧은 트랜잭션을 사용하며, SQLite 잠금 대기는 100ms로 제한합니다. 대시보드 요청은 집계된 DB만 조회합니다.
- 최근 30일을 보관합니다. 오래된 행은 10분마다 테이블당 최대 5,000개씩 정리하므로 삭제가 일시적으로 늦어질 수 있습니다.

스레드가 분리되어도 CPU·디스크는 공유합니다. 이 설계는 작업량을 제한하며, 운영 부하가 0임을 보장하지는 않습니다. 속도는 짧은 순간의 최대값이 아니라 수집 구간 평균입니다. 장기 그래프도 바이트 합계 / 실제 수집 시간 합계로 계산합니다.

## 운영 설정

`/etc/openmmo/server.env`에 필요한 값을 설정합니다. 대응하는 CLI 옵션은 `--network-interface`, `--network-sample-seconds`, `--nginx-access-log`입니다.

```dotenv
# 생략하면 IPv4 기본 경로 중 metric이 가장 작은 인터페이스를 선택합니다.
NETWORK_INTERFACE=ens3
# 기본 60초. 10분으로 바꾸려면 600. 허용 범위: 60~600초.
NETWORK_SAMPLE_SECONDS=60
# 실제 게임 사이트의 access log 경로. 생략하면 파일 순위 수집만 비활성화됩니다.
NGINX_ACCESS_LOG=/var/log/nginx/openmmo-access.log
```

`ens3`는 예시입니다. `ip route show default`로 실제 외부 인터페이스를 확인합니다. IPv6 전용 서버나 정책 라우팅 환경은 인터페이스를 명시합니다. 루프백을 지정할 수 없습니다. 여러 인터페이스를 합산하지 않으므로 브리지·물리 인터페이스 중복 집계를 피합니다.

운영 Nginx는 저장소 밖의 `/etc/nginx/sites-available/openmmo`에서 관리합니다. `nginx -T`로 실제 로그 위치·형식을 확인하고, **게임 사이트 전용 파일**을 연결합니다. 여러 사이트가 함께 쓰는 전역 access log를 연결하면 다른 사이트의 정적 파일도 포함됩니다.

클라이언트 빌드는 해시 파일 생성 후 GLB·JS·CSS·WASM의 `.gz`를 생성합니다.
1024바이트 이상이며 압축하면 작아지는 파일만 대상으로 하고, 원본과 수정 시각을 맞춥니다.
이미지·음악은 제외합니다. 빌드에서 생성한 파일은 `dist/`에만 있으므로 에셋 업로드 대상이 아닙니다.
Docker는 시작 시 로그인 설정을 치환한 JS의 `.gz`도 다시 생성합니다.
게임 사이트의 `server` 블록에는 다음을 설정합니다. Docker 설정도 동일합니다.

```nginx
gzip on;
gzip_static on;
gzip_comp_level 6;
gzip_min_length 1024;
gzip_vary on;
gzip_types text/css application/javascript text/javascript application/wasm;
```

`gzip_static on`은 gzip을 허용하는 요청에 이미 생성한 `.gz`를 그대로 보냅니다.
압축을 허용하지 않으면 원본을 보냅니다. `.gz`가 없는 JS·CSS·WASM에는 기존 동적 압축이
적용되고, GLB에는 원본이 제공됩니다. GLB용 `gzip_types` 추가는 필요 없습니다.
[Nginx gzip_static 모듈](https://nginx.org/en/docs/http/ngx_http_gzip_static_module.html)이
필요하며 `nginx -V`의 `--with-http_gzip_static_module`로 확인합니다.

현재 운영 파일에 사전 압축만 추가할 때는 운영 호스트에서 다음 명령을 실행합니다.
스크립트는 원본을 변경하지 않으며 `.gz`는 임시 파일을 완성한 뒤 교체합니다.
다른 정적 파일 배포와 동시에 실행하지 않습니다.

```bash
sudo node client/scripts/compress-assets.mjs /var/www/openmmo
sudo nginx -t && sudo systemctl reload nginx
```

위 Nginx 설정을 적용한 후 reload하면 되며 게임·NPC 서버 재시작이나 클라이언트 재빌드는
필요 없습니다. 기존 WebSocket 연결은 Nginx의 이전 worker가 계속 처리합니다.
`tools/deploy-prod.sh`는 게임·NPC를 재시작하므로 이 작업만 할 때는 실행하지 않습니다.
이미 게시된 해시 파일의 원본 바이트는 그대로 유지합니다. 최적화한 모델의 새 해시와
manifest 게시 작업은 별도로 진행합니다.

설정 변경 후 `nginx -t`를 통과하면 Nginx를 reload합니다. gzip을 허용하는 실제 GET 응답의 `Content-Encoding: gzip`, `Vary: Accept-Encoding`과 압축 해제한 본문이 원본과 일치하는지 확인합니다. 기존 캐시 정책은 유지하며, 정적 파일 순위에는 압축 후 전송한 본문 바이트가 집계됩니다. 변경 전 전송량은 소급해서 줄어들지 않습니다.

기존 `combined` 또는 저장소의 `combined_cc` 형식은 그대로 읽습니다. 예를 들어 게임 `server` 블록의 로그 설정은 다음과 같습니다.

```nginx
access_log /var/log/nginx/openmmo-access.log combined buffer=64k flush=1m;
```

이미 별도 형식을 사용하는 경우 유지하고, 아래 JSON 형식의 별도 로그를 추가할 수도 있습니다. 추가 로그는 디스크 쓰기도 추가합니다. `log_format`은 `http` 문맥, `access_log`는 게임 `server` 문맥에 둡니다.

```nginx
log_format traffic escape=json
    '{"timestamp":"$msec","method":"$request_method","path":"$uri",'
    '"status":$status,"bytes":$body_bytes_sent}';

access_log /var/log/nginx/openmmo-traffic.log traffic buffer=64k flush=1m;
```

JSON 형식에는 IP·쿠키·토큰·쿼리 문자열을 넣지 않습니다. 기존 combined 로그를 읽을 때도 DB에는 쿼리 문자열을 제거한 파일 경로와 숫자 집계만 저장합니다.

서버 실행 사용자가 로그 및 회전된 로그를 읽을 수 있어야 합니다. Ubuntu에서 로그 그룹이 `adm`이라면 `sudo systemctl edit openmmo-server`에 다음을 추가할 수 있습니다.

```ini
[Service]
SupplementaryGroups=adm
```

실제 파일·디렉터리 권한과 logrotate의 새 파일 생성 그룹도 확인합니다. 이 문서의 설정은 코드 변경만으로 운영에 적용되지 않습니다. 설정 적용 시에는 기존 배포 절차와 운영 데이터 이전 절차를 따릅니다.

### 로그 회전과 재시작

- 처음 로그를 연결하면 현재 끝에서 시작합니다. 과거 로그는 소급 집계하지 않습니다.
- 파일 식별자(device/inode), 읽은 위치, 집계 결과를 같은 DB 트랜잭션으로 저장합니다. 정상 재시작이나 저장 실패 후 재시도 시 같은 행을 다시 합산하지 않습니다.
- `.1`, `.2`처럼 숫자가 붙는 rename 방식 회전을 지원합니다. 아직 읽지 않은 이전 파일을 같은 디렉터리에서 찾아 오래된 순서대로 처리합니다. 다른 회전 이름은 이전 파일을 찾을 수 있어도 중간 순서를 보장할 수 없어 누락 가능 구간으로 표시합니다.
- 로그가 밀렸다면 그만큼 회전 파일을 압축·삭제하지 않고 보관해야 합니다. 디렉터리는 최대 256개 항목까지만 탐색하며 압축 로그는 읽지 않습니다. 이전 파일을 찾을 수 없으면 누락 가능 구간을 기록합니다.
- `copytruncate`는 피합니다. 파일이 짧아진 경우는 감지하지만, 확인 사이에 잘린 뒤 이전 크기 이상으로 자라난 경우는 감지할 수 없습니다.
- 비정상적으로 긴 줄은 제한된 버퍼로 건너뜁니다. 완성되지 않은 마지막 줄은 다음 집계까지 기다립니다.
- 로그를 못 읽어도 게임과 네트워크 수집은 계속됩니다. 대시보드에 집계 중단·지연·건너뛴 줄 수를 표시합니다.

### 측정 범위

- 인터페이스 지표는 Linux 호스트 기준입니다. Nginx 정적 파일·WebSocket·API 외에도 SSH·배포·백업 등이 포함됩니다. Docker 안에서는 해당 컨테이너의 네트워크 공간만 보이므로 호스트 전체 지표로 해석하면 안 됩니다. 운영 기본 구성은 호스트의 systemd 서비스입니다.
- 재시작 후 첫 카운터는 기준값으로만 사용합니다. 인터페이스 교체·카운터 감소·읽기 실패 시 기준을 다시 잡습니다. 중단된 기간의 트래픽을 추정해 채우지 않습니다.
- 계정당 속도는 최근 수집 구간의 송수신 합계 속도 / **구간 종료 시점 접속 계정 수**입니다. 개인별 실측 사용량이 아니며, 0계정이면 표시하지 않습니다. 공식 NPC 제외 등 기존 동접 기준을 따릅니다.
- 정적 파일 비중의 분모는 인식된 정적 파일 본문 전송량 합계입니다. 네트워크 전체나 청구서와 일치하는 값은 아닙니다. API는 제외하며 망토 텍스처 응답은 이미지로 포함합니다.
- 성공한 GET·HEAD와 304 응답을 집계합니다. 206 부분 다운로드는 실제 본문 바이트로 합산하며, 요청 수가 완전한 다운로드 횟수와 같지는 않습니다.
- BGM(`/bgm/`의 오디오), 효과음·기타 오디오, 텍스처·이미지, GLB·glTF, JS·CSS·WASM, 폰트, 기타 정적 파일로 분류합니다. 오류 응답과 알 수 없는 확장자는 순위에서 제외합니다.
- GLB 내부 텍스처는 GLB에 포함됩니다. 브라우저 캐시만 사용한 파일은 서버 전송량이 없습니다. 파일명 해시가 다른 배포 버전은 별도 파일로 표시합니다.
- 파일 순위는 완료된 10분 구간을 합산하고, 전송량 상위 20개를 보여줍니다. 최근 요청이나 밀린 로그가 뒤늦게 반영될 수 있으므로 마지막 로그 확인 시각·미처리량을 함께 확인합니다.
